# Reproducibility and source provenance

## What this archive preserves

The scientific implementation is copied byte-for-byte from
`CINDES_exponential_SCC_overnight.zip`, together with its original numerical
reference-score table. `provenance/package_sources.json` records source hashes.
`protocol_origin.json` records the earlier pilot and sampler-selection provenance.
The separately recovered `submit_scc_fixed.sh` corrects SCC array submission;
it changes scheduler handling, not the scientific configuration or seed plan.

The new `reproduce.py` is a portable command driver. It invokes the existing
preparation, fitting/sampling, and summary entrypoints without changing their
algorithms or hyperparameters. The new README and configuration exports provide
submission-oriented instructions. Original documentation and verification files
are retained under `provenance/`; they are historical records, not new test results.

## Verified final SCC configuration and task plan

The final SCC output metadata supplied by the authors are included without
modification under `provenance/final_scc_run/`:

- `manifest.json`: frozen scientific identity and recorded source hashes.
- `study_config.json`: full scientific configuration.
- `task_plan.json`: all 80 paired-task identities and their RNG seeds.

The manifest's internal identity hash is valid. Its configuration and task plan
agree exactly with the two separate metadata files. Rebuilding the full identity
from the actual packaged scientific files produces the same hash:

```text
6dfb802c5a7d3628cb84b4f111b2eeb62f5f217ec88dc0021ee13db8d75dad96
```

All 14 critical scientific files/assets match the final manifest. The 23 recorded
source entries also match their retained copies: the original README is kept in
`provenance/original_package/README.md`, while this archive has a new submission
README. The separately recovered fixed SCC launcher is not listed in the final
manifest; its changes concern array submission, not the scientific implementation.

The final full-profile task plan contains 20 replication labels, 4000 through
4019, at each of n=500, 1000, 1500, and 2000. Its RNG rules are:

```text
fit_seed = data_seed = 100000*n + replication_seed
fold_seed = fit_seed + 700000
```

The two previously missing tasks retain their original seeds in the final records:

| Task | n | Replication seed | Fit/data seed | Fold seed |
| --- | --- | --- | --- | --- |
| 2 | 500 | 4001 | 50004001 | 50704001 |
| 50 | 1500 | 4009 | 150004009 | 150704009 |

No seed or scientific-code changes were needed when incorporating the final
metadata. `verification/final_run_metadata_verification.json` records the checks
and the hashes of the supplied metadata files. This verifies the code,
configuration, and planned run identities against the final SCC records.

## Reported results versus new outputs

`reported_results/` contains aggregate statistics transcribed from the final
80-pair console summary supplied by the authors. These contain 20 pairs at each
sample size. The precision is that of the supplied console values; runtime values
were printed to three decimal places. These files are neither raw per-replication
results nor outputs generated by the small package execution check.

New runs write their own per-run outputs and newly computed summaries under the
selected output root. The original summarizer reconstructs tables from those
records, using sample SD (ddof=1) and the actual number of completed pairs.

## Computing environment

The original SCC environment is recorded by each run but its final environment
records were not supplied here. `requirements.txt` gives the original minimum
dependencies, not an exact lockfile for the SCC runs. Any environment recorded
under this archive's `verification/` belongs to the packaging check.

Floating-point results and elapsed times can differ across CPU/GPU hardware,
PyTorch/CUDA versions, numerical libraries, and thread configurations. The source
does not globally enable PyTorch deterministic algorithms. The strict source and
artifact hashes protect provenance; they do not guarantee identical numerical
outputs on different devices.
